# 上手与使用

[返回首页](../README.md) · [开发指南](development.md) · [限制与发布清单](release-checklist.md)

## 两种运行方式

- 无渲染模拟：独立 Node.js v26.8.1、npm、完整源码和依赖安装网络即可。无需 Creator；输出测试或 JSON，不提供网页游戏服务。
- 可视预览：另行通过 Cocos Dashboard 安装 **Cocos Creator 3.8.8**。项目已编写场景和动态 UI，但实际编辑器导入、渲染与构建仍待验证。不能用类型检查代替这一步。

Node 其他版本尚无验证矩阵。先在源码根目录检查 `node --version` 与 `npm --version`，不要默认使用 Creator 内置 Node。

```sh
npm ci
npm run sync:core
npm run test:adapter
npm run typecheck
npm run typecheck:cocos
npm run check:cocos-bundle
```

## 导入与首次预览

1. 在 Dashboard 中用 3.8.8 导入源码根目录。版本信息在根 `package.json`，项目设置在 `settings/v2/packages/project.json`；不要按旧计划自行补造根 `project.json`。
2. 等待 AssetDB 导入。打开 `assets/scenes/Battle.scene`；场景的 Battle 节点已关联 `BattleSceneController`。导入后用 3.8.8 保存场景。
3. 确认项目设计分辨率 1080×2400，UI/Graphics 模块可用；选择 **Current Scene**，点击 Play。
4. 先检查“故事模式 / 场景演练”入口。选择模式和场景后进入五兵种编成页，合计1～15人；确认后大屋/楼下有3秒布阵，别墅立即开始。战场居中、约占安全区面积50%，场内对象一起缩小。紫色为普通僵尸；青色为选中与移动指令。上述实际显示仍需编辑器手验。

若脚本缺失或序列化默认值迁移失败，先读第一条导入错误。必要时在 Creator 新建场景、添加空节点 Battle，将 `assets/scripts/adapter/BattleSceneController.ts` 拖到节点，不需 Inspector 参数；保存为原 `Battle.scene` 并保留 `.meta` UUID。组件会自行创建 Canvas 和正交 UI Camera，先移除新场景自带的默认 Canvas/Camera，防止重叠。完整说明见 [Cocos 导入说明](../README-cocos.md#prepare-and-import)。

## 操作

1. 每局先用加减按钮选择五种兵种，合计1～15人。大屋/楼下默认9人、别墅默认7人；确认前不生成僵尸、不计时，会话内按场景记住上次确认的编成。
2. 直接按住士兵拖动，松手移动其整队；近邻120地图像素内、无遮挡的士兵自动成队。选中成员亮圈，文字显示“整队移动 · N 人”，拖动过程中不会因时间长而切为单兵。
3. 要单独移动一名士兵，在他身上原地长按0.45秒，看到白色选择圈和“单兵移动 · 1 人”后再拖动。其他成员继续原有指令；空地起手不会框选或沿途收兵。
4. 释放点与按下点至少相距8屏幕逻辑像素才发命令；最近士兵作为锚点，触摸容错至少18屏幕逻辑像素。手势捕获成员ID，核心过滤死亡成员，移动中经过的其他士兵不会加入。
5. 整队尽量保持相对站位，以最慢成员速度行进，先等待喷火兵收火和工兵拆卸。步枪射程460px、每0.35秒30伤害，可边走边射；喷火射程220px、每0.15秒14伤害，站定持续喷火，移动前0.30秒收火、停止后0.25秒放火。僵尸实际扣血时只在自身闪白0.10秒。墙体、门窗和路径继续遵循各兵种遮挡规则。

第一关大屋南北各有一扇600耐久大门，僵尸攻击破门后进入。三波在0/7/20秒开启，总100/200/400只，每批最多10只、间隔0.60秒，不等清场。楼下四边连续生成720只，每0.35秒10只。别墅四边连续240只，每批1只，60秒内间隔从0.60秒降至0.20秒，需保护中央6名蓝色平民。各场景共享生成限速，暂停或后台后不集中补刷。

轻点、空地按下、拖回起点附近、取消触摸、在 HUD 开始或结束均不能提交移动；非主触点不能接管当前手势，第二根手指不能抢走正在拖拽的控制权。命令手势有 300ms 墙钟冷却。布局变化和切后台会取消持有输入；新一局才重置冷却。

HUD的“暂停/继续”控制战斗，切后台自动暂停，回来主动恢复。“重新开始”和故事下一关均返回选兵页；“返回首页”回到模式选择。故事顺序为大屋、楼下、别墅；各场景生成完且清场后胜利，别墅还要求保护平民。终局停止核心结算，已有死亡淡出可完成。白色十字显示AI目标，不接受点选集火。完整规则见 [本轮设计与实现](14-battle-controls-and-pacing-design.md)。

### 狙击兵与工兵

故事场景的九人小队还包含一名亮蓝色狙击兵与一名橙色工兵。狙击兵绘制带瞄准镜的长枪，开火时有枪口闪光与后坐力，子弹显示亮青色弹道和命中扩散效果；命中后的弹道保留 0.24 秒。子弹速度为 1200px/s，独立存活时间为 0.5 秒，可走完整个 520px 射程。

工兵在开战后停留原地时自动架设机枪；到达新的移动目的地后也会重新架设。架设耗时 2 秒，显示橙色读条，三脚枪架随进度展开；拖动工兵下达移动命令后，先显示 1.5 秒青色拆卸读条并收起枪架，再携枪移动。架设和拆卸期间不能射击，拆卸完成前不能移动；拆卸期间再次拖动只替换目的地，不重置读条。过热时也可以拆卸和转移，冷却仍按原计时继续。读条、动作和移动流程已有自动化检查，Creator 和真机上的实际显示仍需验证。

## 历史验收战术：开局向中部收拢

以下测量来自此前人数和出怪设置，保留作战术示例；当前配置需重新测量，不能据此认定仍有相同胜负或存活人数。

3秒布阵结束、战斗时间0s时，按A/B/C三组活兵的当前质心依次选中，分别拖到墙下方空地(450,1400)、(540,1400)、(630,1400)，共三条正常移动命令。自动化核对每条命令的原始选中ID；另用真实InputManager按下/松手路径验证，保留300ms墙钟冷却。该示例用于当前四向地图，不能保证人工操作耗时不同仍有相同存活人数。

旧版28s/52s两阶段后撤属于历史三通道地图，已不作为当前规则的胜利验收。人数、出怪数和门耐久变化后，过去生成的模拟结果不再代表当前关卡。以新生成的[验收报告](testing/mvp-test-report.json)和测试套件为准；Creator 实际渲染与操作仍需手测。

A/B/C是分组与统计标签，不是固定路线；僵尸每个逻辑步重新寻找可达士兵，沿墙角或门路线追击，目标不可达时尝试其他可达单位。两张故事地图的完整墙体不能翻越；旧地图中显式配置 `stackRequired` 的矮障碍保留堆叠翻越。3秒布阵自动结束，MVP不支持跳过。可选微信短振动已实现，跨线警告同批合并且至少1000ms限频，支持性与物理效果待真机。

`npm run acceptance:report`默认覆盖 [当前报告](testing/mvp-test-report.json)，保留旧证据可使用`-- --output dist/reports/mvp-test-report.json`。后续由用户运行Creator；按 [手测清单与填写模板](testing/cocos-manual-checklist.md)记录，未操作的项目保持“未验证”。

## 构建去向

此仓库没有 npm 启动服务器或已验证的 Creator CLI 发布命令。先同步核心，在 Creator 的 Project → Build 选择 Web Mobile，加入 Battle 作为启动场景，构建并运行。再按 [微信与真机检查](release-checklist.md) 用合法授权的 AppID 构建 WeChat Mini Game，并在微信开发者工具打开导出目录；账号、凭据和界面操作由操作者本地完成，不写入公开仓库。
